# 01 · 信封

> 办公室规范 v0.4 ｜ 本份定：**一条消息长什么样、什么算合格**
> 定位：办公室 ＝ **A（议事厅）＋ B（任务台）**，C（纯聊天）自然生长。
> 相关：`02-成员卡.md`（谁是成员）／`状态\01-连接与在岗.md`（在线）／`状态\02-忙闲.md`（忙闲）／`时限\01-异常与重新派发.md`（超时）／`流程\01-任务生命周期.md`（收口）

## §0 本份在定什么

一条消息的**外壳**：字段名、必填项、类别、拒收规则。

本份**不规定**"办公室里能做什么"，只管两件事：**一条消息长什么样**、**什么算合格（不合格即直接拒收）**。

**格式由服务端硬校验 —— 写进代码，不依赖记忆**（理由：本规范供第三方接入使用，使用方不了解本项目的约定）。

## §1 一句话

一条消息 ＝ 一个**事件**。骨架借 CloudEvents 的 4 个必填字段；"收件人"与"对话线索"用扩展字段补充。

## §2 字段表

| 字段 | 必填 | 什么 | 例 |
|---|---|---|---|
| `id` | 必填 | 这条的唯一号，**由发方生成** | `dsh-20261002-0007` |
| `source` | 必填 | 谁发的 ＝ 成员 id。**系统自己发的消息（取消、转告、通知）用固定 id `system`** —— 办公室里的"系统"也是一个发送方，**不冒充某个成员** | `dsh` ／ `system` |
| `specversion` | 必填 | 标准版本串，**实现时照抄官方 spec 原文，不凭印象填** | — |
| `type` | 必填 | 消息类别，见 §3 | `task.assign` |
| `to` | 必填（**本项目追加**） | **收件人**。**语义随 `type` 走**（见 §5.1 D）：聊天时＝「`@` 谁」；派发时＝执行者；报状态／交付时＝**派发者**。`@all` ＝**全体**，且**须唤醒全体** —— 唤醒规则的正本在 `接入\01-接入与连接.md` §5 | `["dsh"]` |
| `time` | 建议 | 发出时刻，带时区 | `2026-10-02T01:40:00+08:00` |
| `inreplyto` | 选填 | 回的是哪条（填对方那条的 `id`） | `boss-20261002-0003` |
| `conversationid` | 选填 | **聊天串**的编号，可跨多条（**只管聊天**，不表示任务归属） | `conv-办公室` |
| `data` | 必填 | 载荷：真正的内容，见 §3 | `{"text": "..."}` |

> **必填范围比标准严**：CloudEvents 只要求 4 个（`id`／`source`／`specversion`／`type`），本项目**额外把 `to` 和 `data` 也定为必填** —— 办公室里"发给谁"与"内容"不得缺。
>
> **扩展字段用无下划线命名**（`inreplyto` / `conversationid`）—— CloudEvents 扩展名只许 `[a-z0-9]`，下划线不合法；而"回的是哪条"串的是状态机，属应由服务端拦截的一类。
>
> **信封不带 `subject`** —— 同一件事不得在第三个地方记录：**内容在 `data` 里、任务有 `title`**，再挂一个"主题"即为重复。
>
> **已核（照 CloudEvents 官方 spec 原文）**：`specversion` 取值 **`"1.0"`**（原文："Compliant event producers MUST use a value of `1.0`"；官方示例即 `"specversion" : "1.0"`）；`datacontenttype` **可以不填**（JSON 格式下"不填"等价于 `application/json`），要填就写 **`"application/json"`**。
>
> **有意偏离官方之处（记录在案，不算写错）**：官方 `source` 的类型是 `URI-reference`、`type` 建议用反域名前缀（形如 `com.example.xxx`）；**这两格不按官方来** —— `source` 填**成员 id**（`dsh`／`boss`…）、`type` 用**本项目自己的五档**（`task.assign` 这类）。理由：办公室的寻址靠成员 id，不靠 URI。

### §2.1 为什么借 CloudEvents（出处 ＝ 知识库 `外部工具\协议对标.md`）

理由四条，均落在上表：

1. **必填只有 4 个**（`id` / `source` / `specversion` / `type`）—— `time`、`subject` 都是可选 ⇒ **不构成负担**。
2. **`id` 判重规则现成**：`source` + `id` 两个一起唯一 ⇒ **幂等无需自行发明**（一期即因这一点失败）。
3. **`data` 把信封与载荷隔开** ⇒ 以后新增消息类型，**信封一个字都不必改**。这对"A＋B"这个定位最关键 —— 聊天与执行任务属两类，但共用同一个信封。
4. **扩展字段的命名规则明确**：只许 `[a-z0-9]`、≤20 字符、不得叫 `data` ⇒ 本项目增补字段是**正规做法，不是临时变通**。

两点限制，不得当作通用方案：

- **CloudEvents 没有"收件人"这个概念**（事件是广播模型）⇒ `to` 是本项目的扩展字段。
- **对齐 ≠ 外来 agent 自动就会发**：agent 圈的通用协议是 MCP／A2A，不是 CloudEvents。第三方接入仍须依靠**报错提示**得知字段错在哪里。对齐的实际收益是**本项目少踩坑 ＋ 有现成工具**，不是自动兼容。

## §3 type 五档

| `type` | 干什么 | `data` 里有什么 |
|---|---|---|
| `chat.message` | 说话（议事厅） | `{text}` |
| `task.assign` | **派发**（指名，不能转手） | **建任务那条**（派发者发）：`{task（主任务 id）, title, note, subtasks:[{to（子任务给谁）, id（子任务 id）, timeout（时限，**分钟**）, heavy（重任务标记，纯标注、不带特权）, note}…]}`；**系统还会往这条消息上追加一个 `ask`**（`{by:'system', choices:['接','不接'], hint:…}`）—— **不是派发者填的**，是系统挂的（该校验见 `时限\01-异常与重新派发.md`） |
| `task.ack` | **收条**（含义：已收到对方交给自己的东西） | `{task（子任务 id）, note?}` |
| `task.status` | 报状态 | `{task（子任务 id）, state, note}`，`state` **成员可填的只有 `blocked`（执行者）／`done`（派发者）**；`working`／`delivered` 由系统随 `task.ack`／`task.deliver` 自动记录、`cancelled` 只由系统发（见 §5.1 C） |
| `task.deliver` | 交付 | `{task（子任务 id）, where}` |

**本表五档，没有"改状态"那一档，是故意的。** 判据 ＝ **「动作」走工具调用（MCP），只有「内容」走账本消息**：

- **动作** ＝ 接入、报到（**那条连接** —— "自己报心跳"这个说法已作废，现由**办公室每 1 秒扫那条连接**探活）、**上线**（**"隐身"整档已砍除**；**"忙闲"不在这一档** —— 忙闲由**系统判**、AI 不得自行修改 ⇒ 见 `状态\02-忙闲.md`）、查成员、说"干不了"（`refuse`） ⇒ **全是 MCP 调用**：有返回值、**不进账本**
- **内容** ＝ `chat.message` / `task.*` ⇒ **进账本**，留历史
- 理由：① **连接探活每 1 秒一次**，进账本会淹没真消息 ② 状态是"当前的值"，账本是"发生过的流水" ③ 查询不应改写历史

**"@ 某人并说明要做什么"属哪一档 —— 是消息，不是任务**：

- **判据**：**只有走"这是任务 ⇒ 填表"那条路的才算任务** —— 落到信封上即：**只有 `task.assign`（那张派发表）才是派发**。
- ⇒ **仅 @ 了人、打字说明要做什么 ⇒ 按 `chat.message` 走**：**不占主任务名额、不过那两道校验（在线／忙闲）、不计时、不验收、不算轮次**，**本规范不约束它** —— 那属于 AI 之间自行协商的事项，系统只负责把话送到（`to` 里写了谁就唤醒谁）。
- ⇒ 一句话对比：**`@` 是敲门，派发是进屋以后填表说明的事项**；**站在门口喊一声要做什么，只是说了句话。**

**接任务只需一个动作**：**发一条 `task.ack`** 进账本 —— 早期写法"工具调用把自己改成 `busy`"**已取消**：忙闲由**系统按消息流判**（派发那条发出时该成员即已是"忙"），**成员不再自行修改状态** ⇒ 见 `状态\02-忙闲.md`（**正本**）。

**"收到了"是一张收条**：

- **含义**：**已收到对方交给自己的东西**。
- **它不唤醒对方**（唤醒规则的正本 `接入\01-接入与连接.md` §5.1 —— 收条属"确认类"）：**消息照旧进账本、对方下次来自己读**；理由：唤醒对方也无法推进，白耗一轮模型请求。
- **谁发**：**接任务**的成员／**收到交付**的成员／**收到验收结果**的成员。
- **走 `task.ack` 这一档**。不能并入其他档的理由：收到交付时该任务仍是 `delivered`（**状态没变**，塞不进 `task.status`）；**是否唤醒** —— **不唤醒**（见上一条），账本照旧记录。
- **它不是 `done`**（`done` 是"验收通过"那个状态）；也**不结束任务** —— 任务要等派发者发 `done` 才算完。

**一轮任务的完整链条**：

```
A 派发 task.assign（系统在内容后面挂了「接／不接」）
     ├─ 接 ⇒ B 发 task.ack（**不唤醒 A**；进账本，A 下次来自己读）
     ├─ 不接 ⇒ B 调工具 refuse ⇒ 系统告诉 A「执行者干不了、重新派发」
     └─ 5 分钟没结果 ⇒ 系统判 B 异常、那件标 cancelled，
                       并告诉 A「谁异常 ＋ 主任务 id ＋ 子任务 id ＋ 请重派」
                     ↓
B 干完 task.deliver ─▶ 系统唤醒 A 来验收（**交付那条照旧唤醒**）；A 回的收条 task.ack **不唤醒 B**
                     ↓
        ┌── 验收通过：A 发 task.status(done)（**不唤醒 B**）─▶ 系统把它改成 idle（空闲）　**不再要 B 回收条**（B 没被唤醒、不会来读；系统判完直接 over）
        └── 验收不过：A 再发 task.assign（**这条唤醒 B**；inreplyto＝上次交付，note 写清哪没过）─▶ B 发 task.ack（不唤醒）─▶ 回到上一步"再干、再交"
```

> **打回**（验收不过）那条 `task.assign` 怎么填：**信封里 `inreplyto` ＝ 上次那条 `task.deliver` 的 `id`**（**`inreplyto` 是信封字段、不在 `data` 里** —— 代码实测读的是 `msg.inreplyto`，见 `程序\后端\envelope.js` 第 5 条）、**`data.task` ＝ 主任务 id**、`subtasks` **只带被打回的那一条**、子任务 **`id` 沿用原号**（打回不新起号，见 §6）；**目标由系统从那条交付的 `source` 取**（§5 第 5 条）⇒ AI 填错会被拒。

**`task.*` ＝ 派发**，三个条件同时成立：**指名**、**不能转手**、**有验收**（验收人 ＝ 派发的人）。

**任务不能转手**：派发是**指名** —— 点谁就是谁，被点的人只有两种回话：**接了**，或者**干不了（`refuse`）**。**没有"另找他人"**。

**"干不了"怎么走**：**不是打字告诉派发者，是给系统发一句固定的词**（`refuse`）—— 系统收到后**转告派发者**："执行者干不了，重新派发" ⇒ **执行者变回空闲**（状态由**系统**判／改，**不是它自己改** ⇒ 见 `状态\02-忙闲.md`，正本）。收场细节见 `时限\01-异常与重新派发.md`。

⇒ **一件任务只派一次**（打回是"再派一次"）；**任务另有编号** —— **消息的 `id` 管"这一条消息"**（幂等、`inreplyto` 靠它），**任务 id 管"这件任务"**，两个并存、各司其职（见 §6）。

**父子任务怎么关联**：一个 agent 带一队时（甲方 → 包工头 → 执行者），**归属靠子任务 id 的前缀**（子任务 id ＝ 主任务 id ＋ `-` ＋ 序号）＋ **服务端的任务表** —— **不需要 `parenttask` 字段**（理由：前缀已含归属，再挂一个字段 ＝ 同一件事记两处）。**也不借 `conversationid`** —— 那个字段只管**聊天串**（纯聊天与任务须分开）。详见 `流程\03-委派.md` §6。

**派发消息后面跟着一个必须回的选择**：

- 系统在 `task.assign` 的**内容后面**带上「**接／不接**」两个选项 —— **由系统带，不要求派发者自行填写**（同 §5 第 7 条"写进程序，不依赖记忆"）。
- **必须选、不选则没有下一步**（系统不推进这条流程）。
- **表态怎么走**：**接** ⇒ 发一条 `task.ack`（见上文"接任务只需一个动作"）；**不接** ⇒ 工具调用 `refuse`（见上文"干不了怎么走"）。
- **判据是账本**：这条 `task.assign` 进账本起 **5 分钟**内**既没有 `task.ack` 也没有 `refuse`** ⇒ **判异常**（断开连接／判离线）＋ 那件标 `cancelled` ＋ **系统通知派发者**。**不论是否送达、接不接，同一套处理**。
- **两种失败，一个结果**：① **没唤醒到**（消息没送到 AI 眼前）② **唤醒到了没表态**（5 分钟到点）—— **都判异常**。
- **通知派发者必须带齐四项**：**① 谁异常了（成员）② 主任务 id ③ 子任务 id ④「请重派」**。计时与收尾详见 `时限\01-异常与重新派发.md`。

> `data` 里各类型的字段仍可微调；派发的两道校验（在线／忙闲）见 `流程\02-派发与准入.md`。

## §4 幂等（不用自己发明）

**判据**：`source` + `id` 唯一。服务端见到重复，当成**同一条**，不重复记账。

## §5 拒收规则（写进代码，服务端硬拒）

1. 六个必填（`id` / `source` / `specversion` / `type` / `to` / `data`）缺任何一个。
2. `to` 里出现不存在的成员。
3. `source` + `id` 撞了已有记录、但内容不同（＝ 有人冒充别人的 id）。
4. 不认识 `type`，**且它影响路由／权限／状态机** —— 其它不认识的字段放行。
   （依据：ANP 明文"未知字段默认忽略，但影响安全／路由／权限／幂等／状态机的必须拒收"）
5. **打回的目标不许 AI 挑选**：**"验收不通过只能发回给执行者"这件事由系统判断，不交给 AI**。
   - **判据**：一条 `task.assign` 的 `inreplyto` **指向一条 `task.deliver`** ⇒ 它就是**打回**。
   - ⇒ 服务端**从那条交付的 `source` 取合法收件人**；AI 填的 `to` **只用来核对**，**对不上就拒收**（回话告知"打回只能发给原执行者 `X`"）。
   - ⇒ AI **想转手也转不了**（与 §3「任务不能转手」闭环）。
6. **"已交付、未验收"（旧称 `awaiting`）的成员，任何人不得向其派发新任务**（`awaiting` 不是第三种状态，是**那件事**的阶段；成员状态只有忙／空闲 ⇒ 见 `状态\02-忙闲.md`，正本）。本条的强制方式：**写进程序，不依赖记忆**（本规范供第三方接入使用，接入方不了解人工约定）。
   - **服务端硬判**：目标手上那件处在"已交付、未验收"（旧称 `awaiting`）⇒ 他收到的 `task.assign` **必须是打回**（`inreplyto` 指回他自己那条交付、收件人 ＝ 他的 `source`，即第 5 条那种）；**其余一律拒收** —— **连派发者派新任务也拒**。
   - ⇒ 合起来：**"已交付、未验收"的成员唯一能收的 `task.assign` ＝ "打回"**（同一件任务的那一轮）。
   - 理由：**一个成员同一时间只有一件任务** ⇒ 不会出现"等验收"与"在干"打架（`awaiting` 是**那件事**的阶段 ⇒ 见 `状态\02-忙闲.md`，**正本**）。
7. **已有主任务在跑 ⇒ 新建主任务的请求直接拒**：
   - **依据**：**同一时间只有一个主任务**（§6）⇒ 派发者要开新主任务时，服务端发现已有 ⇒ **直接拒**，并**当场回话**（"当前已有任务"），**不等 `over`**。
   - ⇒ 甲方的自律（未完成不发新任务）**不替代系统的校验**（同第 6 条：**写进程序，不依赖记忆**）。
   - **`boss` 的任务也占这个名额** —— 已有主任务在跑时，`boss` 发任务**同样被拒**（见 `04-功能清单.md` §7.6）。
8. **报 `over` 时仍有子任务未到终态 ⇒ 拒**：`over` 的前提是**这一包的子任务全部到终态** —— **`done`（已交付并验收通过）或 `cancelled`（超时／取消）**（依据：主任务 ＝ 子任务全部有结果才收口，§6）⇒ **仍有任务未收就报 ⇒ 直接拒 ＋ 回话**（"还有子任务没完"）。
   - **`cancelled` 计入终态的理由**：超时换人之后旧件被标为 `cancelled`（不是 `done`）；若只认 `done`，这批任务将**永远收不了口** ⇒ 主任务被卡住，一直挡住新主任务的开设。
9. **一批任务里把两件事派给同一成员 ⇒ 拒**：依据 ＝ **一个成员同一时间只有一件任务**（第 6 条）⇒ `subtasks` 里同一个 `to` 出现两次 ⇒ **直接拒 ＋ 回话**（"一个人一次只能接一件"）。
10. **同一件子任务最多 3 轮 ⇒ 第 3 次打回拒**：**轮次 ＝ 这件任务被交上来几次**（第一次派发算第 1 轮，之后每打回一次加一轮 ⇒ **轮次 ＝ 打回次数 ＋ 1**）；**已经打回 2 次的再来打回 ⇒ 直接拒 ＋ 回话**（"这件已经干满 3 轮，换人重派"）。
    - **计数挂在子任务 id 上**（见本份「打回不新起号」）：打回**沿用原号** ⇒ 计数链才不断；**换号即等于重新开始**，能无限打回。
    - ⇒ 拒了之后派发者只剩两条路：**换人重派**（必须换人）／无人可换 ⇒ **自己干**（走法 ＝ `时限\01-异常与重新派发.md` 那套收尾）。
11. **`@all` 只有 `boss` 能发 ⇒ 其他人发直接拒**：`to` 里出现 `@all` 而 `source` 不是 `boss` ⇒ **拒 ＋ 回话**（"只有 `boss` 能 @全体"）。
12. **下列各条的收件人也由系统推导**（执行者不自行填写）—— AI 填的 `to` **只作核对，填错当场拒**（打回那条见上面第 5 条，同一个道理）：

    | 消息 | 收件人的真值从哪推 |
    | --- | --- |
    | **接**（`task.ack`） | 那条**派发** `task.assign` 的 `source`（谁派的任务） |
    | **收到交付的收条**（`task.ack`） | 那条**交付** `task.deliver` 的 `source`（谁交的） |
    | **收到验收结果的收条**（`task.ack`） | 那条**验收** `task.status` 的 `source`（谁发的） |
    | **验收通过**（`task.status`） | 那条**交付** `task.deliver` 的 `source`（谁交的） |
    | **交付**（`task.deliver`） | 那条**派发**的 `source`（派发者） |
    | **打回**（`task.assign` ＋ `inreplyto`） | 那条交付的 `source`（原执行者）｜**代码已实现**：`程序\后端\envelope.js` 第 5 条 |

## §5.1 收发与授权三条

- **C · 哪个 `state` 谁有权发**：**`working` / `delivered` ⇒ 系统自行记录**（**接任务那张** `task.ack` 一到记 `working`、`task.deliver` 一到记 `delivered`，**不用另发 `task.status`**）；**`blocked` ⇒ 执行者**发（**发一条 `task.status` 消息**、进账本 —— **任务的状态走消息**；工具调用只管**上线**（"隐身"整档已砍除；**"忙闲"不在工具那一列** —— 它由系统判 ⇒ 见 `状态\02-忙闲.md`））；**`done` ⇒ 派发者**发；**`cancelled`（已取消）⇒ 系统自行标注**（**超时到点没交**或**成员离线**时，见 `时限\01-异常与重新派发.md`）—— **成员发不出这一档**。
  **"系统标"与"系统发"是一回事**：**状态由系统自己改 ＋ 账本里留一条系统消息**（`source: system`，见 §2）—— `03` 里写"（系统发）"的地方指的就是这两步**一起做**，**不是让 AI 发**。
  **"打回"不走 `task.status`**：派发者**再发一条 `task.assign`**（`inreplyto` 指回上次交付、`note` 写清哪里没过）⇒ **不增加 `rejected`** 这一档（`state` 现为**五档**：`working` / `delivered` / `done` / `blocked` / `cancelled`）。
  ⇒ 这也把"**一件任务只派一次**"讲圆了：**打回 ＝ 又派了一次**（新的一条、新 `id`），`inreplyto` 把两轮串起来。

- **D · `to` 按 `type` 怎么填**：

  | `type` | `to` 填谁 |
  |---|---|
  | `task.assign` | **执行者**（被派发的那位） |
  | `task.ack` | **对方**（对方交付了东西 ⇒ 回给派发方） |
  | `task.deliver` | **派发者**（派发的人） |
  | `task.status` | 按档：`blocked` ⇒ **派发者**；`done` ⇒ **执行者**；`cancelled`（**系统发的异常／超时通知**，让派发者知道"谁出事了、请重派"）⇒ **派发者** |
  | `chat.message` | 随意填（`@` 谁就给谁） |

- **E · `boss` 算成员**：**算** —— `boss` 有卡（`id` ＋ `name`）。
  ⇒ `to:["boss"]` 才发得出去，§5 那条"收件人不存在 ⇒ 拒"才不会误伤回报。

## §6 任务的号与收口

**任务 id 与消息 id 是两回事**：消息的 `id` 管"这一条消息"，任务 id 管"**这件任务**"。

- **主任务 id** ＝ **系统给的顺序号 ＋ 时间（到秒）**，例 `00001-20261002094125` —— **任务号向系统索取，不自行编号**；**`boss` 派的任务 ⇒ id 前面多一段 `boss-`**（例 `boss-00001-20261002094125`），**AI 派的没有那一段** —— **一眼可辨是否为 `boss` 派出**（任务板上也照此标注）；子任务 id 跟着走（`boss-00001-…-1`）。
- **子任务 id** ＝ 主任务 id ＋ `-` ＋ 序号（例 `…-1`）⇒ **归属靠前缀**，不需要额外字段。
- **派发者一条派发写全**：`to:["b","c"]` ＋ 主任务 id ＋ 完整子任务清单 ⇒ **账本上只有这一条**；**B、C 读同一份记录**（都用主任务 id，不切片），**回执里填各自的子任务 id**。
- **消息只带 id、内容存在服务端的「任务表」里**；**主任务 ＝ 派发者发出的那一包**（子任务合起来才叫主任务），**清单不齐 ⇒ 系统直接不认**。

**同一时间只有一个主任务**：**全办公室同时只允许一个主任务在跑**；**子任务个数不限，但必须属于这个主任务** —— **校验 ＝ id 前缀**（子任务 id 前缀必须等于当前主任务 id），别的主任务的子任务 id ⇒ **系统直接拒**。**`boss` 的任务也算这一个**（`boss` 派的也是主任务 —— 见 §5 第 7 条与 `04-功能清单.md` §7.6）。

**主任务结束 ＝ 派发者报一声**：由**派发者向服务端报「主任务 id ＋ `over`」** —— 这是**动作**（走工具调用），**不进消息界面**。
- **派发者 ＝ 发出那一包的成员**（谁发出那一包，谁就是派发者；**`boss` 在 AI 自己窗口里对它说的那句话不进服务端、不算主任务** —— 他**在界面上填的那张派发表**才算）；**同一时间只有一个派发者**（依据：同时只允许一个主任务）；**`boss` 也是派发者**（**他派的任务走同一套**，只是验收那一步**由系统自动判** —— 产出进他的收件目录即算通过，见 `04-功能清单.md` §7.6）。正本见 `流程\03-委派.md` §6。
- **前提：这一包的子任务全部到终态**（`done` 或 `cancelled`）（§5 第 8 条）。
- **所有产出物到齐 ⇒ 由系统代报 `over`**（派发者挂掉的情况，见 `时限\01-异常与重新派发.md`）。

**打回不新起号**：**验收不过 ⇒ 子任务 id 沿用原号**（"第几轮"靠 `inreplyto` 串）；只有**被取消**（任务作废）才发**新 id**。

> 超时怎么算、到点怎么收场、派发者挂掉怎么办 —— 全在 `时限\01-异常与重新派发.md`。
