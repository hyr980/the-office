## §3 忙闲

**定义**：忙闲指成员手上**是否存在未结束的事项**。

### 3.1 判定原则

成员手上存在未结束的事项时，状态为**忙**；不存在时为**空闲**。

### 3.2 状态取值

| 状态 | 含义 |
|---|---|
| `busy` | 手上存在未结束的事项（派出的任务未交付，或已交付未验收） |
| `idle` | 手上不存在未结束的事项 |

### 3.3 状态由服务端维护

- 状态由服务端依据消息流判定并写入，**成员不自行设置**。
- 系统**不提供"成员修改自身状态"的操作**。
- **人工修改入口**：
  - 位置：成员卡内。
  - 流程：修改前须经确认，确认后生效。
  - 权限：该入口仅对 `boss` 开放；成员不可使用。

### 3.4 判定表

服务端依下表判定：

| 事件 | 状态变化 |
|---|---|
| 派发者发出 `task.assign`（点名执行者） | 被点名的执行者变为 `busy` |
| 执行者发出 `task.ack` | 维持 `busy` |
| 执行者发出 `refuse` | 变为 `idle` |
| 执行者已交付、尚未验收 | 维持 `busy` |
| 派发者验收通过（`done`） | 变为 `idle` |
| 派发者异常（5 分钟未回执） | 执行者变为 `idle`，产出转交 `boss`（详见 `..\时限\01-异常与重新派发.md`） |
| 断开连接或下线 | 不可派发，且状态不显示 |

### 3.5 派发者的状态

派发者（持有进行中主任务的成员）状态为 `idle`。

- **依据**：主任务未结束前，任何成员均不得发起新任务，因此不会再有任务派发给派发者，无需占用 `busy`。
- **注意**：派发者实际仍在执行拆解、派发、验收等动作；"账面状态"与"实际是否在忙"是两个概念，不得混同。

### 3.6 状态不显示

成员不在线时，状态栏留空，不显示 `busy` 或 `idle`；派发校验同时拒绝该成员。

成员恢复在线后，依 §3.4 重新判定。（若该成员手上的事项已被服务端标记为 `cancelled`，则判定结果为 `idle`。）

### 3.7 `awaiting` 的含义

`awaiting` 指**事项所处的阶段**，不是第三种状态。

- 「已交付、未验收」记录在账本中、挂在任务上；对**人**而言，该成员此时状态为 `busy`。
- 其唯一用途是**派发校验**：处于等待验收的成员，只有其派发者可再派（即打回），其他成员一律不可派。
  判据见 `..\流程\02-派发与准入.md`（该处为正本）。
- 因此：**状态两态供人与界面使用；"等验收"描述任务进度**。两者不得混同。

**注意**：派发后 5 分钟内既无 `task.ack` 也无 `refuse`，判定为**异常**（属异常判据，不属状态问题），见 `..\时限\01-异常与重新派发.md`。
