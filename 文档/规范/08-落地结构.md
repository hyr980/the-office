# 08 · 落地结构

> 办公室规范 v0.4 ｜ 本份只定：**服务端与界面落在什么技术上、文件怎么摆**
> 本文只记**已定结构**与**实测证据**；未定项写「待定」，不作推测。
> 上游：A–F 六个逻辑问题已在 `01`–`05` 中定下（`03` 为导航页，已拆细）。

## §一 账本存储

**JSONL 追加文件**（一行一条 JSON），**单写者**：仅服务端写入，客户端一律不写。

- 服务端串行写入 ⇒ **不需要文件锁**。
- 选它而不选 SQLite 的理由：新账本只装「内容」（**动作经工具调用执行，不入账本**，见 `05` §2.1），数据量小；纯追加，崩溃安全；可人工阅读、可 grep、可 diff；备份即复制单个文件。SQLite 查询能力强，但需要 schema、无法手工查看，办公室这一量级用不上。
- **实测对应**：`data-layer.js` 使用的即为 `board.jsonl`（`appendFileSync` 追加）。

## §一之二 任务表（即界面上的「任务面板」）

**消息只带 id，内容全在表里。**

- 服务端持有一张**任务表**：**任务 id → 内容 ＋ 子任务清单**（b 的子任务 id、c 的子任务 id…）。
- **消息不装内容**：`task.*` 消息**只带任务 id** ⇒ 收到者**凭 id 到表中读取**。
- **主任务 ＝ 子任务之和**：子任务齐备才构成主任务；**清单不齐 ⇒ 系统不予受理**（拒收）。
- 与账本的分工：**账本**装「发生了什么」（消息流水）；**任务表**装「任务是什么」（内容 ＋ 当前状态）。

**已定项**：

- **id 编码**：**主任务 id ＝ 顺序号 ＋ 时间**（精确到秒）⇒ 例 `00001-20261002094125`；**人派的任务在 id 前多加一段 `boss-`**（例 `boss-00001-20261002094125`），**AI 派发的不含该段** —— 一眼可辨该任务由人派发（任务板上亦按此标注）；子任务 id 随之携带该前缀（`boss-00001-…-1`）；**子任务 id ＝ 主任务 id ＋ `-` ＋ 序号** ⇒ 例 `…-1`、`…-2`。⇒ **由前缀即可知该子任务归属哪个主任务**。**顺序号由系统发放** —— 派发者向系统**申请一个号**（工具调用），系统返回下一个顺序号；**不得自行计数**（全办公室同时只有一个主任务，号由单一方发放才不会重复）。
- **时限为与子任务 id 并列的字段**：**每件子任务各带一个 `timeout`**（不是整个主任务一个值），**由派发者自行填写数值**（**自定义、必填**、**单位＝分钟**、**不与任务类型绑定** —— 该值须进入派发表的标准格式，不得省略）。
- **时限有上限**：**普通任务 ≤ 30 分钟**；**重任务（渲染一类）可一小时以上**。**上限属规则，由派发者自行遵守 —— 系统不校验**；**重任务标记仅为标注**（在清单上标出、日志留痕，**不放行任何内容**；字段名 `heavy`）。
  - **时限不得写入 `note`**（`note` 是自然语言，系统无法解析）；也**不得并入 id 字符串**（id 是身份标识，会被 `inreplyto`／日志／重派引用，并入时限须换号且对不上账）。⇒ **该值由派发者填写，系统读取字段判定「是否按时交付」**（**系统不代为估算时限**）。
- **派发者只发一条**：一条派发表写全（`to:["b","c"]` ＋ 主任务 id ＋ 完整子任务清单）⇒ **账本上仅此一条**，不会出现「B 已收到、C 尚未收到」的中间状态。
- **执行者读取同一份记录**：各执行者收到的**都是主任务 id**，**读取同一份记录**（含完整清单，各成员的任务彼此可见）；**不做切片**。各自认领：记录中 `subtasks` 里 `to: b` 的那条即为 B 的（id `…-1`）。
  - **回执中填写各自的子任务 id**（不是主任务 id）—— 同一主任务下 B 卡住、C 已交付，属**两件子任务各自的状态**，分别记录。
- **同一时间只有一个主任务**：**全办公室同时只允许一个主任务运行**；**子任务数量不限，但必须属于该主任务**。
  - **校验方式 ＝ id 前缀**：子任务 id 的前缀必须等于当前主任务 id；**属于其它主任务的子任务 id ⇒ 系统直接拒绝**。
- **主任务结束 ＝ 派发者发出 `over`**：由**派发者向服务端上报 `主任务 id` ＋ `over`**。**派发者 ＝ 发出该批任务者**（向某人布置的内容在其自身窗口内，**不进服务端**；**同一时间只有一个派发者；`boss` 亦为派发者、走同一套**，其派发的任务即为主任务，仅验收由系统自动判定 —— 正本见 `流程\03-委派.md` §6）。该操作为**动作**（经工具调用），**不在消息界面弹出**。
- **打回不新起号**：**验收不通过 ⇒ 子任务 id 沿用原号**，「第几轮」由 `inreplyto` 串联；仅**被取消**（该任务作废）时发**新 id**。
- **日志须完备**：服务端记录**系统动作**、不记录聊天内容 —— 记录项包括：**拒收（谁、原因）／取消／踢下线（谁、被踢原因）／判派发者异常（谁、判定依据、5 分钟未回「收到」）／判执行者未表态（谁、哪件子任务、派出后 5 分钟无结果 ⇒ 判异常）／`over`／状态变化**，各项均带**时间戳 ＋ 主／子任务 id**；**每个子任务已跑轮数亦须记录**。形式：**按天一个文件、只追加**，与账本分开（**账本**＝消息流水，**日志**＝系统动作）。**「被踢原因」须留痕**：① **写入日志**（主要途径）；② **系统可同时告知当事人**，但**仅说明其触发了哪一条规则**。
- **「清单不齐 ⇒ 系统不予受理」的校验点**：建立主任务时必须同时登记完整子任务清单，**缺项 ⇒ 该派发直接拒绝**。

## §二 服务端形态

**独立进程**（不以 DSH 插件形态内嵌），**开关由 `boss` 掌控**。

- 因此**不实现为 DSH 插件** —— 若做成插件，开关便不在 `boss` 手中。
- **开关形式**：**不采用「托盘图标单独开关后端」的方式** ⇒ **规则：打开壳 ⇒ 后端随之启动；关闭壳 ⇒ 后端随之关闭**（`boss` 无需单独管理后端）。
- **关闭办公室 ＝ 真正关闭**：服务端是唯一入口，办公室未启动时 AI 发消息直接返回「办公室没开」。
  - 该规则在多口接入下的落实方式 ⇒ 见 §四。

## §三 界面

**PowerShell 壳 ＋ WebView2 独立窗口**。

**两条总则**：

- **AI 面向命令台；界面面向 `boss`** ⇒ 界面的判据是「**`boss` 一眼看得明白、点得到**」，不是「信息是否齐全」。
- 形态照**微信／QQ**（成员列表 ＋ 聊天区）；**侧边栏两条**（成员在线／离线与忙／空闲、任务板）；**日志在界面内查看**；**文件夹点击即打开** —— 细节全部在 `04` §7。

**选用 WebView2 的理由**：满足全部约束 —— 独立窗口（非浏览器标签）、**零额外依赖**（Win11 自带运行时）、**与壳同属一个 PowerShell 进程**、可绘制复杂界面。

## §三之二 目录结构

**不使用传文件**：**全部在同一台机器上**，在程序根目录下建立若干文件夹即可，**交付即交目录、并说明位置**。
⇒ **产出物 ＝ 本地目录中的文件**；消息中**只给路径**，不搬运内容、不走通道。

**四条硬分类**：

    <办公室程序根目录>\
      ├─ 收件\<主任务 id>\      ← 两类：兜底转来的 ＋ `boss` 自己派的任务的产出（见下）
      ├─ 产出\<成员 id>\<日期>\ ← 各成员向自己的目录写入，按天严格分类
      ├─ 日志\                  ← 按天一个文件（界面内按天翻阅，见 `04` §7.3）
      └─ 数据\                  ← 账本（board.jsonl）＋ 任务表

- **目录名用中文** —— `boss` 一眼可辨；Windows 路径支持中文。
- **收件目录存放两类**：① **兜底转来的产出**（派发者已停止、产出物只能转交至 `boss` 处的情形）；② **`boss` 自己派发的任务的产出**（见 `04-功能清单.md` §7.6 —— 其任务判「验收通过」的依据即为产出物进入该目录）。**AI 之间正常交付的产出不进入此处** —— 正常产出位于**成员自己的产出目录**，交付时报**该路径**，由派发者（或打回后的派发者）读取。
- **成员产出目录按天严格分类** ⇒ `产出\<成员 id>\<日期>\`。
- **收件目录按主任务分子目录** ⇒ `收件\<主任务 id>\`。
- **成员只能写自己的产出目录** ⇒ 因此**在 `boss` 的任务中，执行者照旧写入自己的产出目录、交付时报路径**，**由办公室将产出归入** `收件\<主任务 id>\`（否则「产出进入目录 ＝ 验收通过」这一判据无法落地）；同一流程中，**「收到」亦由系统代 `boss` 回执**（验收既然自动判定，收条无需等待人）。**此两条已由 `boss` 确认。**
- **交付判据**：成员交付 ＝ **报一个目录路径**；界面将该路径**高亮**，`boss` **点击即用资源管理器打开该文件夹**（**打开的是文件夹，不是文件** —— 见 `04` §7.4）。
- **上述四个目录由程序首次启动时自行建立** —— 规范中写「待建」之处即指此事，**无需手工预先建立**。

## §四 桥接方案 —— 接法最后实现

**该部分明确安排在最后实现。**

> 依赖应当采用本机已有的；此事不急，先把其余部分完成，再考虑如何接入。由于涉及多 agent，各家接法不同，需要找到一种所有 agent 都可用的接法，或至少在一组候选接法中有一个可用。

⇒ 设计原则：**服务端对外暴露多种标准口**，各 agent 自行选择适配，不绑定任何一家 SDK。
先例（旧 `room_server`）：同时开启 **stdio MCP ＋ 8787 HTTP**（两个客户端分别走 HTTP 与 stdio，双向闭环已实测跑通）⇒ 「多种接法中至少一个可用」可以做到。

### 多口接入的三条约束

- **后端只由系统启动一处**：后端由**系统**启动（即**打开壳**，见 `§二`）。**接入方不得自行启动后端**，亦不得各自维护状态（谁在线、谁在哪个会话）。
- **接入口只是通道**：HTTP／stdio／后续新增的接入口**地位平等**，都只是进入的路径。**无论经哪个口进入，进入的都是同一间办公室**（同一份账本与同一份任务表）。
- **后端未启动时，任何接入口均不可用**：一律按 `§二`「关办公室＝真关」报「办公室没开」。
- **落实判据**（用于检查实现）：① 全系统只有**一个**写账本的进程；② 任一口单独存活而后端未启动时，**它不能执行任何操作**；③ 从任一口进入者，看到的**账本／任务表／在线名单完全一致**。

> **实测缺口（2026-10-03 验收 M8 记录）**：当时 dsh 所使用的 stdio 口**自建了一套** —— `mcp-stdio.js` 在每个进程中各 `require('./bridge')`（每个进程各持一份桥），会话映射为内存态。实测后果三条：跨口叫醒不通（发出结果为 `delivered:[]` ＋ `silent:[{reason:"无会话（等报到后轮询收件箱）"}]`）；办公室未启动（`GET /health` 不通）时它仍可报到、发消息、叫醒；并与壳启动的后端同写同一份 `数据\`。⇒ **按本节改为「只连不建」**。
>
> **同日已修（2026-10-03）**：`mcp-stdio.js` 主入口不再 `require('./bridge')`，改为仅作代理 —— 工具调用走 `POST /api/call`、工具清单走**新增的** `GET /api/tools`（客户端位于 `程序\后端\http-client.js`），**连接不通即返回「办公室没开」**（即 `§二`「关闭办公室 ＝ 真正关闭」的口径）。工具调用与工具清单均改为支持异步（本地桥为同步、HTTP 客户端为异步，两者皆支持）、请求**串行**（工具会改写账本，不得并发交错）；同时修复了 EOF 时 `process.exit(0)` 冲掉未排空 stdout 的缺陷。验收脚本 ＝ `验收\M8c-多口接入.ps1`，**6 项通过、0 项未通过**（跨口叫醒 `delivered:[{…,wake:true}]`／办公室未启动时 `isError:true` ＋「办公室没开」／办公室未启动时 `数据\` 不写入任何字节）。该脚本**必须用 PowerShell 运行**：node 中 spawn 带管道的子进程会被沙箱拦截（EPERM）；本机执行策略为 Restricted，运行方式为 `powershell.exe -NoProfile -ExecutionPolicy Bypass -File …`。
>
> **接入连接端点**（设计要求：由系统统一检查各接入端是否仍在连接，**每 1 秒一次**）：`GET /api/alive?memberId=` —— 接入端启动后即挂上该条（服务端推送的流）并**一直不关闭**，该连接**即**其「在线」凭据。办公室侧 `bridge.js` 维护一张接入连接表（`attachAlive`／`detachAlive`／`sweepAlive`），挂在原有 ticker 上**每 1 秒扫描一遍**：向每条连接写入一个字节 ⇒ 写入成功 ＝ 其仍在（同时刷新存活时间）；写入失败或已断开 ＝ 其已掉线。**接入端不再自行发送心跳**（`程序\接入\` 下那个最小接入桥当时改为挂连接版本、**该脚本已于 2026-10-05 删除**；`mcp-stdio.js` 在首次代替某成员调用工具时替其挂上，无需改动宿主的拉起方式）。刷新仍走 `status.receiveHeartbeat` ⇒ **被 `boss` 踢下线者连接照旧挂着、状态不变，只能由 `boss` 叫回（`call_online`）**（该句已于 2026-10-04 作废，见本条之后的「再修正」）。判定只在这一处 ⇒ 即「一套心跳同时监测所有接入口」。
>
> **2026-10-04 修正**：上述「**接入端启动后即挂上该条**」**已作废** —— 已取消自动重连 ⇒ **接入端启动后不得自行挂连接**，须**由人点击「连接」**才挂。**其余判据仍然有效**（每 1 秒扫描一遍、向每条连接写入一个字节探活、判定只在这一处）。同段括号里「**`mcp-stdio.js` 在首次代替某成员调用工具时替其挂上**」那句**同样作废** —— 该行为已移除（见 `程序\后端\mcp-stdio.js` 内注释），且该口本版本走不通（见下条「stdio 口（MCP）的当前状态」）。
>
> **2026-10-04 再修正**：上述「**被踢下线者……只能由 `boss` 叫回**」**同样作废** —— **现行判据见 `接入\01-接入与连接.md` §2.2 的分界线表（正本）**；本段仅为**历史记录**，不得据以编写代码。

- **零依赖**：仅使用 node 内置模块，不 import 任何 `@deepseek-ai/*` ⇒ DSH 升级时不易被带崩（文件头注释即写明此意）。
- **唤醒机制正确**（仅指**该旧插件在其自身的 DSH 版本上**）：`agent.send(message,'next-turn',true)` —— **第三个参数才是唤醒**；`agent.inject()` 不唤醒。**当前 DSH 的宿主服务目录中没有 `agent.send`**（2026-10-03 核实），现行做法是 `sessionController.prompt({ …, mode: 'queue' | 'steer' })`（见 `接入\02-插件职责.md` §1.1）。
- **三重防重复投递**：固定 `message.id`（`room-<seq>-<账本id>`）＋ 本实例的 `recentlyDelivered` Set ＋ 投递前查目标 inbox ⇒ 此为出现「同一条被投递 2~3 次」（`seq=21`）之后补上的措施，README 中有记录。
- **回声保护**（`by == selfId` 不投递）、**连续唤醒预算上限**（`maxConsecutiveWakes: 3`）、**lastSeen 游标落盘**、**文件截断重扫** —— 防重投／防漏读的细节齐备。

**对新办公室不适用的**：

- **判据针对旧账本格式**（`kind`／`by`／`data.to`／`v`）⇒ 新办公室使用信封（`type`／`source`／`to`），此部分**须整段重写**。
- **只投递 `chat.message`** —— 而新规则中恰恰是 `task.*` 需要**唤醒**。
- 默认 `delivery: 'quiet'`（不唤醒）—— 与**现行唤醒规则**（**只看 `to`** —— 正本见 `接入\01-接入与连接.md` §5.1）**相反**。

**硬伤（新办公室必然遇到）**：

- `targetSessionId` **写死为一个会话 id** ⇒ 只能投递给**一个** DSH 会话。
- README 自述：「目标会话不在 registry 时**跳过投递并记日志**（`AgentFactory.resume` 的 `ownerCtx` 未实证，一期不实现）」⇒ **DSH 重启后会话 id 变化即无法投递**。
- 新办公室需要投递给**多个**成员（dsh 等）⇒ 必须补一张**「成员 id → 会话 id」的映射**，这是旧桥完全不具备的。

## §五 三条贯穿的设计原则

1. **依赖只用本机已有的**。
2. **接法最后实现，且须通用**（见 §四）。
3. **不留临时件、不留技术债**：
   - **临时件须当场清理**：先凑合使用的日志／副本／旁路／双份实现，**正主实现完成即当场替换、当场删除**；**不得写「以后再对齐」**。
   - **判据**：合入代码前搜索 `临时`／`暂时`／`先这样`／`以后再`／`待对齐`／`兼容用` 这类注释 —— **有一条清一条**，要么当场完成、要么删除。
   - **实测教训（2026-10-03 验收 M7 挖出）**：`timeout.js` 的 `defaultLog` 注释写着「M7 正式日志模块落地后再对齐」，**M7 完成后该步未做** ⇒ 日志成为两本（`.jsonl` ＋ `.log`）、同一事件记录两遍、轮次数无法统计。
     - **同日已统一（2026-10-03）**：`timeout.js` 删去 `defaultLog`，事件经 `toLogEvent` 归并进 M7 的 7 个固定词（原事件名存于 `extra.event`），只写 `日志\<日期>.jsonl`；`bridge.js` 的 `read_log` 只读这一本。
     - **7 个固定词**：`reject`／`cancel`／`kick`／`dispatcher-dead`／`over`／`state`／`retry` —— **正本**＝`程序\后端\log.js` 的 `EVENT_TYPES`；**写入其它词当场拒掉**，原事件名一律进 `extra.event`。
   - **「一步到位」的口径**：改动一个临时件时，**凡与之相关之处须一并改完**（写入它的、读取它的、识别它的词表），**不得留下「半本」痕迹**。
