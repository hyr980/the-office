# 原理说明 —— 各项设计背后的机制

按「为什么」组织。总纲：**ZCode 的插件接口面较窄** —— 可以声明 hooks、MCP 服务器、斜杠命令，
但**不具备** Claude Code 的几个专有接口（`$.tool.register` 动态注册宿主工具、`$.prompt.submit` 向
运行中的会话投递内容、`ui.render` 的输入框上方按钮带）。本插件的全部降级设计均源于此。

## 1. 为什么通过 MCP 递送工具

AI 可使用的工具只有两条来源：宿主内置（插件无法触及）或 **MCP 服务器**（`.mcp.json` 声明）。
而办公室的工具是**动态清单**（`GET /api/tools`，一个不经准入校验的读口）⇒ MCP 服务器在
`tools/list` 时实时拉取清单，在 `tools/call` 时经控制口转发至常驻进程的内核，最终 `POST /api/call` 至办公室。
**表格填写发生在办公室侧**，插件仅提供通路、不代填（AI 无法得知的门牌号与宿主进程名两格除外）。

## 2. 为什么必须有一个常驻进程

- 「常驻连接」是 **SSE**（`GET /api/alive`，持续读取、永不结束）；
- 五个**反向端点**（办公室向插件推送 wake／interrupt／online／connect／challenge）需要有人**持续监听一个端口**。

ZCode 的 hook 与 MCP 服务器都是按事件或请求拉起的**短命子进程**：无法持有不结束的流，也无法保证长期存活。
⇒ 协议全部放在**常驻进程**（`office-host.mjs`，一个 detached 的 node 进程，内核运行其中）；
hook 与 MCP 仅承担三项轻量工作：上报会话、执行按钮动作（请求控制口 HTTP）、转发工具调用。
控制口**仅监听 127.0.0.1、仅接受 POST** —— 它能修改绑定、能投递内容，因此不对局域网开放。

hook 与 MCP 定位常驻进程的方式：指针文件 `~/.office-zcode/office-runtime.json`（`pid`／`ctlPort`／`hostPort`）。
ZCode 没有「插件模块」可以替常驻进程读取 stdout，故参照插件的 stdout 协议在此换为**落盘指针**。

## 3. 为什么「两个按钮」落为五个斜杠命令

《说明书》§1 第 7 项要求的「输入框上方两个按钮」依赖 Claude Code 的 `ui.render`／`AbovePrompt` 渲染位 ——
ZCode 没有该渲染位 ⇒ 按钮落为**斜杠命令**（`/office-connect` 等五个；本质是提示模板，AI 收到后调用
对应的 MCP 工具）。两项代价已在 README 如实注明：**每次执行消耗一轮模型调用**（ZCode 机制决定）；
命令展开属于 TUI 侧行为，headless 模式下不展开。

## 4. 为什么「叫醒」是另起一个进程、而非投递给运行中的界面

ZCode 没有「向运行中的会话投递内容」的接口 ⇒ 叫醒 ＝ `node zcode.cjs -p "<进来看看>" --resume <绑定的会话id> --json`：
**另起一个 headless 进程延续该会话**。下推的仅为「进来看看」这条命令、**不携带正文**
（正文在办公室账本中，AI 进入后自行读取）—— 此为《说明书》确定的形状。

两个已知后果（均需明确说明）：
- 该回合运行于**不可见的后台进程**，不在任何打开的 TUI 中 —— 绑定指向哪个会话，叫醒即恢复哪个；
- headless 回合能否真实完成取决于账号档位：**免费额度下被服务端拒绝**（`turn.failed`／`coding plan is required`），
  需 Coding Plan 档位。机制层面（进程启动、会话恢复）已验证，端到端**未验证** —— 详见《验收到哪一步.md》。

## 5. 为什么「绑定」＝命令在哪执行就绑定哪

hook（SessionStart／UserPromptSubmit）将 `session_id` 上报给常驻进程作为「**当前会话**」；
`/office-online` 绑定的即最近上报的那个 —— **执行命令的会话必然是最近的**。
两层分离：**连接**（第一层）仅建立链路、不涉及绑定；**上线**（第二层）绑定会话＋报到＋在岗；
**下线**仅撤销「在岗」、不解除绑定（会话地址保留，办公室在成员卡上执行「叫它上线」时仍可定位）。

## 6. 为什么成员卡的 model/icon 采用当前的提交方式

办公室的成员卡为**静态目录、权威在服务端**：`register` 提交后才写入（`reportIdentity` 非空才覆盖、
`setIcon` 提交后才写入），回传的四格卡（id/joined/name/icon）即「接入手续」，此后每次建立连接均需携带核对。⇒

- **icon**：《说明书》的硬性要求「第一次上线必须提交（取自宿主进程的图标）」；办公室界面写死
  `data:image/png;base64,` ⇒ 提交的必须是 **PNG 图片本身**的 base64（不是路径、也不是 ico 字节）。
  插件采用三级来源：显式 `iconFile` 配置 → 宿主安装目录自带的应用图标（`resources\icon.png`，
  由 `zcodePath` 反推，自动选取时做 PNG 魔数校验）→ PowerShell 抽取宿主 exe 关联图标（与 DSH 参照插件同款）。
- **model**：仅为成员卡上的一格**显示标签**，不影响连接、唤醒与派发 ⇒ **配置项照报、留空不报**
  （留空时办公室卡上保留旧值）。不在宿主内做「扫描会话流水自动探测」 —— 为一格显示标签引入对
  会话文件路径的脆弱依赖，收益不成立（曾实现、经评审后移除）。

## 7. 为什么单实例、固定门牌号端口

相同数据目录仅允许一个常驻进程（指针新鲜度 ＋ pid 探活，后启动者见到即自行退出）—— 避免双条 SSE 与端口争抢。
门牌号端口固定 19400 才能**跨重启不漂移**（办公室记录该地址）；被占用时先重试两次再退让，退让后门牌号变更一次、
需等待下一次报到。`~/.office-zcode/office-bridge-state.json` 存储的卡为**接入手续**：对已建卡的 id，
办公室要求接入时必须携带，缺失将被当场拒绝 —— 因此该目录不可删除（更换成员 id 重新接入时才删除）。
