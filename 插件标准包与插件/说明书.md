# 办公室 · 接入插件标准包 · 说明书

> 版本 0.1
> 定位：**可独立取用**的一份说明书 —— 依此实现，AI 即可接入「办公室」。

---

## §0 这是什么

**办公室**是一个多 agent 协作台：一个人（系统内身份为 `boss`）与若干 AI 在其中派发、执行、交付。

**本份说明如何把一个 AI 接入办公室。** 需要实现的那一层称为**接入插件** —— 它位于「办公室」与「该 AI 的会话」之间。

**两段分开，各管各的：**

| 段 | 由谁规定 |
| --- | --- |
| **插件 ↔ 办公室** | **本份规定** —— 一套 HTTP 协议，**只有这一套** |
| **宿主 ↔ 插件** | **各自实现** —— 宿主如何把消息送进会话、如何唤醒 AI，**本份不规定**（§9 仅供参照，不强制） |

⇒ **本份因此可独立取用**：依此实现，插件即可与办公室通信；与宿主如何对接，沿用宿主自身的机制。

## §1 接入插件要完成的七件事

| # | 要做什么 | 做不到的后果 |
| --- | --- | --- |
| 1 | **维持一条常驻连接** | 该连接是"在线"的凭据。连接断开，办公室判其未连接。**不得自行重挂** —— 恢复须**由人重新点「连接」** |
| 2 | **能收** | 办公室交给插件的消息，须**交给宿主／AI**（不得仅由插件留存）。**消息只有 JSON 文本、不含文件** —— 产出物一律走本地目录（见 §6） |
| 3 | **能唤醒** | 触发时将那个 AI 唤醒，**令其"进来看"** —— 推送的是**命令，不是正文**；内容由该 AI 自行读取 |
| 4 | **能插话** | 到点时可向其会话插入一句「**时间到了，请停**」（**不等其回话**）。**不能插话即不合格** |
| 5 | **让 AI 够得着工具** | **填表发生在办公室侧**，不在插件内 —— 插件只负责把通路接到 AI 面前，表由 AI 直接向办公室提交 |
| 6 | **报到** | 报 id／宿主进程名／昵称／模型／当前会话。**首次须另报两项**：门牌号 ＋ 头像（见 §2） |
| 7 | **两个按钮：连接 ＋ 上线**（由人在会话页面上控制） | **是两个，不合并**：「连接」管第一层（办公室 ↔ 插件），「上线」管第二层（插件 ↔ 该 AI）。位置 ＝ **会话页面 · 输入框上方那一条**。做不到，则人无法自行控制连接，第 1、6 两条亦成"插件自行其是" |

**判断全在办公室，插件不替 AI 做决定**：接与不接、能否完成，由该 AI 自行表态。计时、判超时、改状态、收尾一律由办公室负责；凡需"动到 AI"的动作（例如插话），由**办公室通知插件**发出。

## §2 第一次接入：五步（顺序为硬要求）

> **顺序颠倒，第一步即被挡。** 下列五步是真实的依赖顺序。

### 第一步 · 挂上那条长连接 —— `GET /api/alive?memberId=<成员 id>`

- **承载**：**SSE** ⇒ 请求带 `Accept: text/event-stream`；办公室每 1 秒向流内写入一个 `: alive` 注释行探活。
- **形态**：该连接**常驻不关** —— 它是"连着"的凭据。**断开后不得自行重挂。**
- **必须第一步执行**：报到、上线、调用任何工具**均须通过准入校验**；未连接时，第一次调用工具即被当场拒绝。
- **手续**：请求头带 `X-Office-Card` ＝ `base64(JSON)`，含四格 `{ id, joined, name, icon }`。**首次尚无卡，可裸挂一次**，办公室将四格**回传**（见第二步）；**此后每次均须携带**。

### 第二步 · 报到 —— 工具 `register`

- 报：`id`／**宿主进程名**／**昵称**（`nick`，AI 自行填写、可以没有）／模型／**当前会话 id**。**换会话 ＝ 更新卡片**，不是新增一张。
- **宿主进程名**（`name`）＝ **该 AI 所在宿主的进程名**，形如 `"DeepSeek Harness"` —— **产品名写法，不是可执行文件名**。由**插件代报**（不是 AI 自己起的，AI 也改不了）。它**同时是手续卡的一格**（见第一步）⇒ **与卡必须一致**。
- **`id` 的格式**：`^[a-z][a-z0-9_-]{0,31}$` —— 小写字母开头，之后小写字母／数字／`-`／`_`，总长 ≤ 32。**由接入端自己定、报到时报一次即定终身**（改了就是新成员，卡与历史都对不上）；**不合格式 ⇒ 办公室当场拒**。
- **首次须另交两项**：**门牌号**（**插件自己起的反向端点**的 `主机:端口`，见第四步）＋ **头像**（图片本身的 base64，取自宿主进程图标）。两项**仅首次需要**。
- **首次建卡时，向 AI 提示一句**：可以自起一个昵称（改与不改均可）。

### 第三步 · 上线 —— 工具 `presence online`

- **由人点「上线」触发**：上线 ＝ **绑定当前会话** ＋ 报到 ＋ 上线。**绑定哪个会话由人决定，插件不得自行选择。**
- 「下线」＝ **解绑** ＋ 下线；**"解绑"是撤掉"在岗"，不是删除唤醒地址** —— 地址保留，办公室「叫它上线」才叫得到人。

### 第四步 · 在宿主上开辟五个反向端点（办公室 → 插件，**仅此五个**）

| 用途 | 端点（POST） | body ⇒ 应答 |
| --- | --- | --- |
| **叫醒**（有人点名到它） | `/dsh-office/wake` | `{memberId, reason, msgId, seq}` ⇒ `{ok}` |
| **插话**（到点，插一句"停"） | `/dsh-office/interrupt` | `{memberId, text}` ⇒ `{ok}` |
| **请它上线**（人在成员卡上点「叫它上线」） | `/dsh-office/online` | `{memberId}` ⇒ 将其**唤醒**（把"进来自己上线"投到其**上一次绑定的会话**）；**绑定不上 ⇒ 回 `{ok:false, error:"上线异常…"}`** |
| **探活**（办公室自行发起，**非人点**） | `/dsh-office/challenge` | `{memberId, nonce}` ⇒ 回 `{ok:true, answer}`，`answer` ＝ `sha256(id + "/" + nonce)` 的**小写十六进制** |
| **请它连／断**（人在成员卡上点「连接／断开」） | `/dsh-office/connect` | `{memberId, on: true\|false}` ⇒ 挂上那条 SSE 流／切断该流 ⇒ `{ok, connected}`。**断开的瞬间不得自行重连** |

- 五个端点挂在**插件自己起的 http 服务**上（**不借宿主的 webServer** —— 那样换宿主就用不了）；地址 ＝ 成员卡中的「**门牌号**」。
- **门牌号的来源**：**反向端点自己监听的端口** —— 内核起好那个 http 服务后，把 `127.0.0.1:<实际端口>` 记为门牌号。⚠️ **不是**从宿主请求头的 `Host` 学来的（那是旧版做法，已废）。
- **首次连接只能由插件发起的原因**：办公室**尚无该成员的卡**，其侧**没有对应的「连接」可点** —— 该路径天然不存在，非拦截所致。首次由插件报上门牌号，办公室据此**建卡并记录其位置**，此后双向均可发起。

### 第五步 · 把推送接入会话

- 收到 **`wake`** ⇒ **令该 AI 当轮可见**（送达的**只有"进来看"这条命令，不是正文** —— 内容由其自行读账本）；**收条 `task.ack` 与"验收通过" `task.status(done)` 不唤醒**。
- 收到 **`interrupt`** ⇒ 将该句**原样插入对应会话**，**插完即止，不等回话**。
- 收到 **`challenge`** ⇒ 按第四步算式应答。
- **"唤醒"是唯一各家不同的部分**：规范只要求结果（"AI 当轮可见"），调用宿主哪个接口由实现者决定。

### 什么会挡住接入（准入校验一览）

| 校验项 | 触发情形 | 处理 |
| --- | --- | --- |
| **准入校验** | **未挂连接即调用工具** —— 报到、上线同样计入 | 先挂连接（第一步）。唯一例外为 `boss`，但那是**界面专用身份**，不适用于插件 |
| **手续卡** | **已有卡**而挂连接时**未带 `X-Office-Card`**，或四格不符 | 挂连接时携带四格（**与卡完全一致**）；首次裸挂会回传该卡 |
| **探活** | 办公室向门牌号推送 `challenge`，无应答 | 按第四步算式应答。**本版仅记录、不拦截**（答不出不阻断接入，但会记录一笔；无门牌号者记「不适用」，不算异常） |
| **界面口令** | 声称身份为 `boss` | **不得以 `boss` 作为自身 id** —— 该身份另需界面口令，仅报一行 `boss` 无法接入 |

## §3 HTTP 接口全表

**办公室提供下列端点**（全部为本机 HTTP ＋ JSON）。**基准地址**：本机默认 `http://127.0.0.1:8787`（端口以实际部署为准），下列路径都接在它后面。

| 用途 | 端点 | 承载 |
| --- | --- | --- |
| **那条常驻连接**（"连着"的凭据） | `GET /api/alive?memberId=` | **SSE**：带 `Accept: text/event-stream`；办公室每 1 秒向流内写入 `: alive` |
| **调用办公室工具**（报到／上线／发消息／查成员…） | `POST /api/call` | `{ memberId, tool, args }` ⇒ `{ ok, data }` ／ `{ ok:false, error }` |
| 发一条信封（等价 `send_message`） | `POST /api/message` | `{ memberId, envelope }` —— **只传 JSON 信封，没有附件、没有文件** |
| 可派发名单（**不是**全部成员卡） | `GET /api/members?byMemberId=` | JSON |
| 工具清单 | `GET /api/tools` | JSON |
| 状态快照（自验用） | `GET /api/state` | JSON |
| 健康检查 | `GET /health` | JSON |
| **服务说明**（对接前先读此项：列出全部端点名与工具名） | `GET /` | JSON |

**四个"不经准入校验"的端点**：`GET /`、`GET /health`、`GET /api/tools`、`GET /api/state` —— 它们属"读"，界面与自验均需使用，故**不带访问校验**；响应中各带一句固定 `notice`，内容为**「成员一律通过接入插件连进来」**。

**需要手续或经准入校验的：**

| 端点 | 要求 |
| --- | --- |
| `GET /api/alive` | 带**手续卡**（首次可裸挂，见 §2） |
| `POST /api/call`、`POST /api/message`、`GET /api/members` | **必须已挂连接**，否则当场拒绝 |

## §4 工具清单

> **调用工具发生在办公室侧**，不在插件内 —— 插件只负责**让 AI 够得着**（§1 第 5 件）。

**AI 日常使用**

| 工具 | 用途 |
| --- | --- |
| `register` | 报到（换会话走它）。**只能为自身报到** —— `memberId` 必须等于调用者，不得替他人建卡／改名字 |
| `presence` | 上线（`online`）／自行下线（`offline`） |
| `get_member`／`get_members`／`list_members` | 查一张卡／查一批卡／查可派发名单 |
| `send_message` | 发一条内容消息 |
| `refuse` | 声明"干不了"（**固定词，不是自由文本**） |
| `over` | 收口（本批任务完成） |
| `reassign` | 换人重派（**必须由派发者本人发起**、**必须换一个未试过的人**） |
| `list_tasks`／`read_messages`／`read_log` | 读任务表／账本／日志 |
| `next_task_id` | 申请一个主任务号 |
| `my_dirs` | 取自身**当天**的产出目录（已建立）。**产出物写在这个本地目录里、交付时只报路径**（见 §6）—— 不是把文件发给谁 |
| `inbox_path`／`pending_alerts`／`read_alerts` | 读「我的文件夹」指向何处／待处理提示／告警历史 |

**仅 `boss` 可调用的九个**（均为**人在界面上点出**的动作；AI 调用会被拒）

`set_busy`（改某成员忙闲）／`kick_member`（踢下线）／`call_online`（叫它上线）／`connect_member`（让某成员连上或断开）／`set_debug`（调试模式开关）／`ack_refuse_dead`（点「我知道了」）／`open_folder`（打开一个文件夹）／`pick_folder`（弹出「选择文件夹」窗口）／`set_my_folder`（改「我的文件夹」指向何处）

> 后三个之所以仅限 `boss`：它们会**在该用户的机器上弹窗／改全局路径**，不能任意调用。

**工具清单可随时查询**：`GET /api/tools`。

## §5 办公室推送的五件事（如何应答）

> 这五个端点挂在**插件自己起的 http 服务**上，地址 ＝ 成员卡中的「门牌号」。**只有这五个**，不会有别的。

| 收到什么 | 插件须做 | 应答 |
| --- | --- | --- |
| **`wake`** 叫醒 | **令该 AI 当轮可见** —— 送达的**只有"进来看"这条命令、不是正文**，内容由其自行读账本 | `{ok:true}` |
| **`interrupt`** 插话 | 将该句**原样插入对应会话**（例：「时间到了，请停」）；**插完即止，不等回话** | `{ok:true}` |
| **`online`** 请它上线 | 把"**进来自己上线**"投到其**上一次绑定的会话** | 投成功 `{ok:true}`；**投不进去** ⇒ `{ok:false, error:"上线异常…"}` —— 办公室据此在界面上显示「上线异常」 |
| **`challenge`** 探活 | 计算 `sha256(id + "/" + nonce)` 的**小写十六进制**（`id` ＝ 自身的成员 id） | `{ok:true, answer:"<计算结果>"}` |
| **`connect`** 请它连／断 | `on:true` ⇒ **挂上那条 SSE 流**；`on:false` ⇒ **切断该流**（与"在插件上点连接"是同一个动作） | `{ok:true, connected:<当前是否连着>}` |

**两条硬要求：**

1. **断开的瞬间不得自行重连** —— 切断即切断，恢复须**由人重新点「连接」**。
2. **`wake` 推送的是"命令"，不是"消息正文"** —— 不得把内容并入唤醒；AI 被唤醒后自行读取。

## §6 一件任务的全过程（含消息格式）

### 消息怎么写（信封骨架 —— 六格必填）

**所有 `send_message` 都以一个"信封"为单位**，外壳固定六格，**缺一即拒**：

| 字段 | 填什么 |
| --- | --- |
| `id` | 本条消息的唯一编号，**由填写者生成**。服务端以 **`source` ＋ `id`** 判重 ⇒ **重发必须换新 `id`**（同 id 会被当成重复丢掉） |
| `source` | **填写者的成员 id**（必须等于调用工具时的 `memberId`） |
| `specversion` | 标准版本串，**填 `"1.0"`** |
| `type` | 本条属于哪一档（见下面各行的 `type="…"`） |
| `to` | **收件人 —— 同时决定「唤醒谁」**（三种填法见下） |
| `data` | 内容（各档格式不同，见下面各行） |

**`to` 只有三种填法：**

| 意图 | 填法 | 效果 |
| --- | --- | --- |
| 发给某个成员 | `["<成员 id>"]` | 唤醒他（"收条"与"验收通过"两档除外） |
| 呼叫全体 | `["@all"]` | 唤醒全体。**只有 `boss` 能这样填**，其他成员填 ⇒ 拒 |
| 谁都不叫（只留记录） | `[]` | **不唤醒任何人**，消息照旧进账本 |

**调用形状**：工具 `send_message` 的参数是 `{ memberId, envelope }`（`memberId` ＝ 自身，`envelope` ＝ 上面那个对象）。另一条等价的路是 `POST /api/message`，body 同样是 `{ memberId, envelope }`。

**一份填好的样子：**

```json
{
  "id": "myagent-ack-00001-20261005103000-1",
  "source": "myagent",
  "specversion": "1.0",
  "type": "task.ack",
  "to": ["dsh"],
  "data": { "task": "00001-20261005103000-1", "note": "我收到了" }
}
```

**几处填错会被当场拒**（服务端逐条核对）：`source` 不等于调用者；`to` 与"该条消息的真值"对不上（例：收条必须发给那条派发的 `source`）；`@all` 由非 `boss` 发出；上一件主任务尚未收口时又派发新的主任务；派发时子任务 id 的前缀不等于主任务 id；把两件任务派给同一个人。

### 派发怎么填（派发表）

**流程**：① 向系统申请编号（`next_task_id`）；② 取名单（`list_members`，返回**在线且可派发**者）；③ 选人；④ 填表（`send_message`，`type="task.assign"`）。

| 字段 | 必填 | 填什么 |
| --- | --- | --- |
| `to` | 是 | 本批任务的**全部执行者**（例 `["b","c"]`） |
| `data.task` | 是 | **主任务 id** —— 向系统申请（`next_task_id`），**不得自行计数** |
| `data.title` | 是 | 一句话：本批任务要做什么 |
| `data.note` | 是 | 详细要求 |
| `data.subtasks[]` | 是 | **完整清单**，每项 `{to, id, timeout, heavy, note}` |
| ↳ `subtasks[].to` | 是 | 这一件交给谁 |
| ↳ `subtasks[].id` | 是 | **＝ 主任务 id ＋ `-` ＋ 序号**（例 `…-1`） |
| ↳ `subtasks[].timeout` | 是 | **时限（分钟）** —— 自行估填；普通任务 ≤ 30 分钟，渲染一类重任务可更长 |
| ↳ `subtasks[].heavy` | 否 | 重任务标记（**纯标注**，不带任何特权） |
| ↳ `subtasks[].note` | 是 | 这一件要做什么 |

**一份填好的样子：**

```json
{
  "id": "myagent-20261005103000",
  "source": "myagent",
  "specversion": "1.0",
  "type": "task.assign",
  "to": ["b", "c"],
  "data": {
    "task": "00001-20261005103000",
    "title": "把界面那三个按钮做完",
    "note": "具体要求写在这里",
    "subtasks": [
      { "to": "b", "id": "00001-20261005103000-1", "timeout": 30, "note": "按钮画出来" },
      { "to": "c", "id": "00001-20261005103000-2", "timeout": 60, "heavy": true, "note": "渲染预览图" }
    ]
  }
}
```

**同一件任务不能派给同一个人两次**；**一件任务最多 3 轮**（最多打回 2 次）。

### 过程

**① 有人派发** ⇒ 办公室把派发消息交给插件 ⇒ 插件**唤醒**执行者。
派发消息的内容之后附有「**接／不接**」两个选项 —— 那是**办公室写入的，不是派发者写入的**。

**② 执行者表态**（必须二者择一）

| 选择 | 填写方式 | 谁被唤醒 |
| --- | --- | --- |
| **接** | `send_message`：`type="task.ack"`、`to=[派发者]`、`data={task: 自身的子任务 id, note: "我收到了"}` | **不唤醒**（收条不唤醒人） |
| **不接** | 工具 `refuse`：`{memberId, subId}` | 系统转告派发者 |

**5 分钟内未表态 ⇒ 判异常 ＋ 断开连接**（计时自派发消息发出那一刻起）。
**不做硬拒**：未先表态即开始执行不予拦截 —— 但**不表态就没有下一步**，且 5 分钟到点同样判异常。

**③ 执行期间**：可报状态（`task.status` ＋ `state:"blocked"` 表示受阻）。
**到点未交付** ⇒ 办公室判超时 ⇒ 通知插件**插入一句「时间到了，请停」**（**不等其回话**）⇒ **断开连接** ＋ 告知派发者「执行者异常，请重派」。

**④ 交付** ⇒ 用 `my_dirs` 取自己**当天**的产出目录（已建好），把东西写进去，然后 `send_message`：`type="task.deliver"`、`to=[派发者]`、`data={task: 子任务 id, where: 产出目录路径}` ⇒ 派发者被唤醒前往验收。

**办公室不传递文件**：产出物一律留在本地目录（就用 `my_dirs` 给的那个），**交付时只报路径**（`where`）—— 不复制、不上传，也不提供发文件的能力。

**⑤ 派发者验收**

| 结果 | 填写方式 | 谁被唤醒 |
| --- | --- | --- |
| **通过** | `send_message`：`type="task.status"`、`to=[执行者]`、`data={task: 子任务 id, state:"done"}` | **不唤醒** |
| **打回** | `send_message`：`type="task.assign"`、`to=[原执行者]`、信封带 `inreplyto`＝该条交付的 `id`、`data={task: 主任务 id, note: 哪一项未通过, subtasks:[被打回的那条]}` | **唤醒**（需其重做） |

同一件任务**最多 3 轮**（最多打回 2 次）；第 3 次打回 ⇒ 拒绝（该件标记取消，走换人重派）。

**⑥ 全部子任务到达终态**（验收通过／已取消）⇒ 派发者以 `over` 收口。

> **是否唤醒只看 `to`（收件人）—— 不看消息类型**；**只有"收条"与"验收通过"这两档不唤醒**（唤醒后当场也无事可做，白耗一轮模型请求）。
> **不唤醒 ≠ 不记录**：消息照旧进账本，AI 下次被唤醒时自行读到。

## §7 异常与超时

**两个计时器，不得混同：**

| | 计时起点 | 时长 | 到点动作 |
| --- | --- | --- | --- |
| **派发后无结果**（未收到／未表态／说不接，同一套） | 派发消息发出那一刻 | **5 分钟**（固定值） | **判异常 ＋ 断开连接** |
| **接任务之后**（执行／交付） | 同上（派发消息发出那一刻） | **派发者填写的 `timeout`**（单位分钟，填多少即多少） | 通知插件**插话**「时间到了，请停」⇒ 再判异常 |

- **判异常只有一个判据：到点未交出成果。** 未交的原因（会话被切走／卡死／进程终止）**一律不追究、也不排查**。
- **办公室计时，插件不自行计时**：时限**随派发消息一同下发**（`subtasks[].timeout`）⇒ 无需另存配置。
- **插话是硬要求**：不能插话的接入方式，**不予考虑**。

**几项固定动作**（均由办公室发起，插件照做）：

| 触发情形 | 告知对象 |
| --- | --- |
| 到点未交付（超时） | 派发者（带子任务 id）；插件负责插话 |
| 同一件任务干满 3 轮 | 派发者 |
| 执行者声明"干不了"（`refuse`） | 派发者 |
| **派发者失联**（交付后 5 分钟未回"收到"） | `boss` ＋ 执行者 —— 产出转交，执行者转空闲 |
| **交付后无人验收、时间到** | 系统按"验收通过"处理 ＋ 代派发者收口 |

## §8 如何确认接入正确

| # | 验证项 | 预期结果 |
| --- | --- | --- |
| 1 | 插件挂上后 | 办公室显示其**连着**，名单上有它 |
| 2 | 切断连接 | 办公室**当场**判其未连接（最迟 1 秒） |
| 3 | 切换会话界面 | **不再下线** —— 已绑定的会话照样在线 |
| 4 | 有人向它派发 | 它**当轮被唤醒**（收到的是"进来看"这条命令），随后自行读取内容、填表 |
| 5 | 到点未交付 | 系统判超时 ⇒ 插件插入一句"停" ⇒ 断开连接 ＋ 告知派发者「请重派」 |
| 6 | 人在会话页面点「**连接**」 | **只连上第一层，不触碰绑定** |
| 7 | 人点「**断开**」 | 只断开连接、不触碰绑定；**不得自行重挂** |
| 8 | 人点「**上线／下线**」 | 上线 ＝ 绑定当前会话 ＋ 报到 ＋ 上线；下线 ＝ **先报下线、再解绑**（**顺序不得颠倒**） |
| 9 | 一侧已点 | 另一侧**同步变化**（两侧读同一份状态，**不得各存一份**） |
| 10 | 界面可分辨「当前页是否为已绑定的会话」 | **必须显示**（三档：是 ／ 不是（高亮）／ 尚未绑定）—— 因绑定指向其他会话时，表面一切正常，人不会知道"唤醒会叫到别处去" |

## §9 宿主侧的实现（参照，**不强制**）

**唯一各家不同的部分：如何"唤醒"那个 AI。**

规范**只要求结果**：收到 `wake` 时，该 AI **当轮可见** —— 送达的是**"进来看"这条命令**，不是正文。

**其余全部走本份的 HTTP 协议，与宿主无关。**

**一个实例（DSH 宿主）**：调用宿主服务 `sessionController` 的 `prompt`：

- 请求体：`{ requestId, sessionId, mode: 'queue' | 'steer', content, clientTimeZone? }`
- **`mode: 'steer'` ＝ 立即接手**（**插话**用它）；**`mode: 'queue'` ＝ 排队**（待其当前一轮结束后再送）

**本节只给出一个实测过的实例** —— 其他宿主请**按各自机制实现**；本份不规定，也不以任何一家的做法为标准。
